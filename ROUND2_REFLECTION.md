## 1. What was the most uncomfortable trade-off you made because of the time pressure?

The re-audit flow creates a new audit ID. When a user clicks the re-run link and gets fresh recommendations, that fresh audit is stored as a brand new row with a new ID — meaning their "updated" result lives at a different URL than the original. The technically correct approach would be to version audits: same base ID, with a version number or `parent_id` pointer, so a user can always get to their latest audit from the original URL. I knew this when I built it. I chose not to do it because it required a schema change beyond what the assignment strictly needed, and because fixing the ID logic in the re-audit route would've taken 2-3 hours I didn't have. The result works end-to-end, but the UX has a real gap: if a user bookmarked their original audit URL, clicking re-run gives them a new URL they'd have to re-bookmark.

## 2. If we extended the deadline by another 24 hours right now, what's the first thing you'd do?

Fix the audit versioning problem described above. Specifically: add a `parent_audit_id` column to the `audits` table, populate it when a re-audit is stored, and update `/result/[id]` to check if a newer version exists and surface a banner ("A newer audit is available — view updated results →"). This one change would make the re-audit feature feel complete rather than functional-but-rough. Everything else — cron scheduling, click tracking, the public pricing change page — is additive. The versioning fix is the one gap that makes the core feature feel unfinished.

## 3. Looking back at your Round 1 codebase as a now-experienced user of it: what's one thing your Round 1 self made harder for your Round 2 self?

The `runAudit` function in `audit-engine.ts` returns a fresh `AuditResult` with a new `nanoid()` on every call. That made sense in Round 1 — each audit run is a new result. But in Round 2, running a re-audit means calling `runAudit` again with the same input, which generates a new ID immediately. I had to work around this by storing the original ID separately and handling the "new ID problem" in the result page. If Round 1 had separated ID generation from the audit logic — or accepted an optional existing ID — the re-audit route would've been cleaner. Not a big deal in isolation, but it's the kind of thing that compounds: every place I needed to "re-use" an existing audit, I had to think around the ID generation instead of just calling the function.
